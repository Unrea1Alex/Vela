# RouteAudit

RouteAudit проверяет пакет маршрутов в NDJSON. Для каждого он рассчитывает
длину, максимальный шаг и число скачков, а затем сохраняет отчёт TSV.
Координаты задаются на плоскости в метрах.

## Сборка и запуск

Из корня Vela 0.10.0-dev.7 или новее на Windows x64 с MSVC:

```powershell
New-Item -ItemType Directory -Force apps/route-audit/bin | Out-Null
.\vela.cmd build apps/route-audit/main.vela -o apps/route-audit/bin/route-audit.exe
.\apps\route-audit\bin\route-audit.exe apps/route-audit/demo.ndjson apps/route-audit/demo-report.tsv
```

В [демо](demo.ndjson) три маршрута. В [готовом отчёте](demo-report.tsv)
маршрут «Парк 🌳» содержит один скачок. Его максимальный шаг равен 10 м.

Входной файл содержит один JSON-объект на строку:

```json
{"name":"Набережная","jump_limit_m":5,"points":[[0,0],[3,4],[6,8]]}
```

Файл читается порциями по 8192 байта через один дескриптор. Строки проверяются
как UTF-8 после склейки порций. Допускаются BOM в начале, CRLF, пустые строки и
последняя запись без перевода строки. Лимиты — 2 МиБ на вход, 64 КиБ на строку,
4096 маршрутов и 1 МиБ на отчёт. В маршруте от 2 до 256 точек. Координаты
ограничены диапазоном ±1 000 000 м, порог — больше 0 и не больше 3 000 000 м.
Имя занимает от 1 до 96 байт и не содержит ASCII-управляющих символов.

Скачок — шаг строго больше порога до округления. В отчёте расстояния
выводятся с двумя знаками после точки. С флагом `--fail-on-jump` наличие
скачка даёт код 3 после сохранения отчёта. Обычный успех даёт код 0.
Ошибки ввода, командной строки и файловых операций дают код 2. Ошибка
разбора сохраняет предыдущий отчёт и указывает физическую строку и путь,
например `line 3: $.points[1][1]: expected number`. Запись идёт через
атомарную замену после закрытия входа. Выход, ссылающийся на вход, отклоняется.

## Проверка

```powershell
.\vela.cmd test apps/route-audit/tests.vela --json
pwsh -File apps/route-audit/verify.ps1
```

Прошли 8 именованных тестов и 10 CLI-сценариев. Отдельно проверены точные
байты отчёта при принудительном GC, повторное использование буфера после
раннего выхода с ошибкой и самостоятельный запуск со стандартным системным
`PATH`. [Результаты](validation.json).

[Прогон памяти](soak.vela) проверяет повторную обработку одного журнала из
256 маршрутов в одном процессе. При 10 и 80 повторах пик управляемой памяти
составил 1 049 166 и 1 055 814 байт соответственно. Это замер heap Vela
для этого набора данных. Размер процесса и память ОС в него не входят.

## Что показала разработка на 0.8

Типизированные JSON-курсоры позволили указать ошибочную координату без
собственного обходчика JSON. `float_sqrt` и `float_to_fixed` закрыли
геометрию и вывод. Переиспользуемый builder и `defer` дали одну точку
сброса буфера для успеха и раннего возврата через `?`.

Чаще всего приходилось вручную переводить ошибки библиотеки в тип,
который принимает вызывающий код. Для коротких приложений достаточно
локальных функций. При появлении вызываемых значений стоит проверить
типизированные преобразования ошибок на таком приложении, включая
сохранение причины и позиции.

У форматтера есть воспроизводимый пример для 0.9.8. На `route.vela`
самая длинная строка выросла со 104 до 126 символов. В сигнатуре с
`Result<T, json::At<json::DecodeCause>>` добавились пробелы вокруг
вложенных generic-скобок. Форматирование пяти файлов идемпотентно, и
собранная из них версия дала байтово тот же отчёт. Этот модуль подходит
для проверки переносов и вложенных типов при работе над форматтером.

Для более крупных журналов полезно рассмотреть ограниченное чтение
строк в файловом API. Здесь лимит в 2 МиБ позволяет читать файл целиком.
Потоковый вариант должен сохранить номер физической строки, разбирать
UTF-8 и CRLF на границе блоков и сохранять атомарную публикацию. Это
прикладное расширение для файловых сервисов, а порядок 0.9 и 0.10
сохраняет смысл. [План](../../docs/ROADMAP.md).
