# Разработка PulseDeck на Vela 0.11.0

Исторический отчёт о первом варианте приложения. Текущие исходники после
1.0.1a используют task groups и awaitable HTTP; прежние выводы сохранены как
основание пунктов roadmap, а не описание текущей реализации.

Проверка от 2026-11-07. [Приложение](README.md), [контракт](CONTRACT.md),
[результаты](validation.json). Язык и runtime в этой работе не менялись.

## Что получилось

Vela уже позволяет написать небольшой отзывчивый сетевой инструмент. В одном
приложении работают нативное окно, несколько HTTP-запросов, HTTPS с проверкой
сертификата, таймеры, отмена и сервер на Vela. Три фактически перекрывающихся
запроса подтверждены независимым сервером. Ошибки отдельных сервисов не срывают
остальные проверки. При отмене завершённые результаты остаются в отчёте.

`Result` и явные эффекты помогают держать ошибки и системные действия на виду.
`defer` работает и после отмены async-задач. В профиле видны шесть вызовов и
завершений warm-up, в отчёте — шесть очисток. Суммарное inclusive-время около
6,9 секунды включает перекрывающиеся ожидания; это не длительность запуска.

JSON cursors дают координаты ошибочного поля. Манифест ресурсов и
`path::resource_base()` убрали необходимость изобретать поиск настроек от cwd.
Отдельный `panic` в generic test-helper наконец позволяет написать завершающий
путь без фиктивного возвращаемого значения. Готовая программа работает без
установленного компилятора.

Проверка проекта с существующим пустым кэшем заняла 172 мс, повторная — 39 мс.
Созданы 14 записей. Это локальная пара замеров, не сравнительный benchmark.
Шесть страниц query собрали те же 7792 записи, что полная выдача. Инструмент
честно сообщил об исключённом тестовом корне; тесты запускались отдельно.

## Что мешало

**Композиция async пока слишком ручная.** Таймеры используют `async/await`,
а HTTP — `start/poll/cancel/release` и другой типизированный scheduler. Пришлось
написать очередь допуска, таблицу активных запросов, сбор результатов, отмену
обоих циклов и очистку. Это рабочий контракт 0.11, но для следующего приложения
хочется awaitable HTTP/process и общего владельца группы задач. Нельзя просто
завернуть текущий `poll` в async: внутри есть синхронное чтение файлов, которое
checker справедливо не разрешает в приостанавливаемом графе.

**Кэш плохо объясняет своё состояние.** Сначала был передан ещё не созданный
каталог: две проверки заняли 152/153 мс, ошибок не было и файлов кэша не появилось.
Это моя ошибка использования: требование существующего каталога есть в PROJECTS.
Но диагностический hit/miss и причина недоступности сделали бы её заметной сразу.
Build-helper приложения теперь создаёт каталог, а проверка инструментов проверяет
реальное появление записей.

**GUI требует повторения C-обвязки.** Для окна переиспользована и адаптирована
Win32-основа FieldDesk; прикладная логика целиком в Vela. Это лучше отдельного
UI-фреймворка для каждого примера, но общий небольшой модуль с pump, кнопками,
текстом и жизненным циклом был бы полезнее очередной копии адаптера.

**Сетевой API пока узкий.** URL собирается из отдельных частей, клиент делает
GET, запрос запускает отдельный curl; loopback-сервер выдаёт фиксированный
Content-Type. Для мониторинга это приемлемо. Авторизация, POST, произвольные
заголовки, streaming и пулы соединений потребуют новых контрактов. Эта проверка
не измеряет пригодность транспорта для высокой нагрузки.

**Простой enum нельзя сравнить через `==`.** Даже состояние без payload
получает E201. Исчерпывающий `match` работает; в приложении состояния хранятся
как enum, а несколько предикатов используют явное отображение варианта в строку.
Хотелось бы короткой проверки варианта или ограниченного равенства таких enum,
с явно заданными границами, без неявного глубокого сравнения любых значений.

## Что менять в плане

Добавлены [1.0.1a–e](../../docs/ROADMAP.md): композиция async и очистка,
диагностика кэша, общий GUI-слой, границы HTTP API, проверка вариантов enum.
Это открытые задачи на контракт и решение о реализации до фиксации API.
Не все расширения обязательно помещать в 1.0: перенос должен быть явным,
с сохранением действующего поведения и описанием миграции.

Менять всю модель языка, вводить наследование или новый backend по итогам
PulseDeck мне не требуется. Наибольший выигрыш сейчас даст более удобная
композиция существующих возможностей и уменьшение системной обвязки.

Проверены Windows x64 и текущий масштаб экрана. Linux GUI/сеть, несколько DPI,
отдельная чистая Windows, длительный нагрузочный прогон и новая холодная сессия
другого агента в эту проверку не входили. Полный compiler verify не повторялся:
compiler/runtime не менялись; приложение пересобрано и проверено отдельно.
