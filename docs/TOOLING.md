# Интерфейс для инструментов

Команда `vela api SOURCE_OR_PROJECT --json` возвращает проверенный
public-интерфейс entry-модуля без требования main. `vela api --builtins` читает
embedded-каталог. Generic/effect signatures, методы и скрытые opaque-поля
обрабатывает frontend; C compiler не участвует. `tools/help.vela` генерирует
единый `docs/api-index.json`. [Контракт](contracts/AGENT-ENTRY-1.2.md).
Нативный `bin/vela-api.exe` выполняет поиск в этом индексе с purpose/ownership
метаданными. MCP `vela_get_help(topic="api", query=...)` передаёт запрос ему;
алгоритм поиска не находится в TypeScript. [Протокол](contracts/API-SEARCH-1.2.md).
`vela init DIRECTORY [--name NAME] [--kind cli|library] [--json]` создаёт
готовый проект в новом каталоге; `vela --help` показывает краткий CLI.
Имена проверяются до записи; существующие назначения сохраняются.
[Контракт и JSON](contracts/PROJECT-INIT-1.2.md).

Активный интерфейс — `vela.cmd` / `velac.cmd` / `bin/velac.exe`. Нативный компилятор поддерживает `check --json`, `symbols`, `emit-c`, `build`, `run` без Python. Служебный параметр `--source-name NAME` задаёт имя виртуального исходника независимо от временного пути. Исторический Python frontend 0.2, его API и обёртки удалены из текущего дерева; для интеграции используйте документированные CLI/LSP/MCP протоколы.

## Подсветка в VS Code

[Расширение Vela Language](../integrations/vscode/README.md) автоматически
выбирает режим Vela для `.vela`. Подсветка работает локально по правилам TextMate
и не требует запуска компилятора. Для диагностики используйте `vela check`.

## Проверка с JSON

В 0.7 команда `vela test SOURCE|PROJECT --json` возвращает report schema 2:
ok/passed/failed/tests; у каждого теста name/source/span/status/exit_code,
stdout/stderr, stdout_encoding/stderr_encoding (utf8 либо hex), artifact_dir.
Status: passed, failed, timeout, build_error. Exit 0 — успех, 1 — провал теста,
2 — инфраструктура; ошибки исходника сохраняют diagnostic schema 1/exit 1.
Тесты выполняются в отдельных временных cwd; созданные ими файлы остаются в
указанном artifact_dir. Это обычное native-выполнение с правами пользователя.
Схема 1 старого project test является исторической. [Контракт](contracts/TESTING.md).

```powershell
.\velac.cmd check examples/invalid/missing_effect.vela --json
.\velac.cmd symbols examples/factorial.vela
```

Успешная проверка возвращает `schema_version: 1`, `ok: true`, путь `source` и пустой массив `diagnostics`. При ошибке языка `ok: false`, в массиве одна диагностика:

```json
{
  "code": "E209",
  "severity": "error",
  "message": "Call to 'print' requires undeclared effects: io.",
  "source": ".../missing_effect.vela",
  "span": {
    "start": 0,
    "end": 0,
    "line": 1,
    "column": 1,
    "end_line": 1,
    "end_column": 1
  },
  "notes": [],
  "details": {"callee":"print","required_effects":["io"],"allowed_effects":[],"missing_effects":["io"]},
  "related": []
}
```

Координаты выше иллюстративные. `start`/`end` — смещения Unicode code points в нормализованном исходнике, полуоткрытый интервал. Строки и столбцы начинаются с 1. CRLF и одиночный CR преобразуются в LF, UTF-8 BOM удаляется. Это **не** смещения байтов и не UTF-16 позиции LSP. Адаптер редактора должен явно преобразовывать координаты. При ошибке доступа к файлу или декодирования возвращается `E900`; координат исходника у неё нет.

Нативный JSON записывается UTF-8: не-ASCII символы сохраняются, кавычки, обратная косая черта и управляющие символы экранируются. Потребитель должен декодировать UTF-8 независимо от кодовой страницы терминала. Нельзя определять категорию ошибки по английскому тексту: используйте `code`.

В 0.4 диагностики дополнены `details` и `related` без смены schema_version.
E201 сообщает `expected_type`/`actual_type`; E209 — `callee`, `required_effects`,
`allowed_effects`, `missing_effects`; E216 — `missing_variants` в порядке объявления.
`related` содержит `{message,source,span}` для связанных объявлений. Поля применяются
там, где такая информация имеется; пустые объект/массив допустимы. Человеческий вывод
включает соответствующие пояснения и позиции. [Полный контракт](contracts/DIAGNOSTICS.md).

## Форматирование

```powershell
.\velac.cmd fmt examples/collections.vela
.\velac.cmd fmt examples/collections.vela --check
.\velac.cmd fmt examples/collections.vela --write
```

Без флага команда выводит канонический UTF-8/LF в stdout. `--check` возвращает 0
для уже отформатированного файла, 1 при необходимости форматирования и ничего
не записывает. `--write` атомарно заменяет исходник после проверок. Флаги взаимоисключающие,
`-o` для fmt не поддерживается. C-компилятор не нужен. Ошибки синтаксиса/UTF-8
оставляют исходник неизменным; семантически ошибочный, но разбираемый исходник
форматировать можно. [Правила и гарантии](contracts/FORMATTER.md).

## Индекс символов

`symbols` сначала проверяет всю программу, затем выдаёт определения перечислений, параметры функций, типы результатов, эффекты, строку объявления и число контрактов. `contracts.verification` равен `runtime`: контракты проверяются при исполнении, не доказываются статически. Для графа использования и идентичности символов в выбранной ревизии служит `query`; проверяемые планы правок доступны через `plan` и LSP (см. ниже).

В 0.10.2 запись закрытой структуры получает `opaque: true`; индекс исходников
может показывать её поля для навигации внутри модуля владельца.
В 0.10.3 методы получают `method: true` в `symbols` и `query`. У закрытого
метода также есть `visibility: "module"`. Планы переименования используют одну
декларацию для обоих видов вызовов.

В 0.3 JSON дополнен массивами `structs` (имена и поля с типами) и `distinct_types`
(имена и базовые типы). Типы коллекций выводятся канонически, например
`Dict<NodeId,List<String>>`. `schema_version` остаётся 1: новые поля добавлены
совместимо, прежний `enums` содержит только перечисления.

В 0.5 индекс содержит конкретные generic-экземпляры с каноническими именами,
например `Box<Int>` и `identity<String>`. Неинстанцированные шаблоны не являются
проверенными функциями и не включены в массив functions. ID C-символов не служат
публичными идентификаторами индекса. Диагностика внутри интерполяции указывает
на исходное выражение, включая Unicode code-point координаты.

## Повторная проверка и пакетная сборка

`vela check ROOT --cache DIR`, `vela emit-c ROOT --cache DIR` и
`vela build ROOT -o OUTPUT --cache DIR` используют локальный каталог доверенного
кэша. С 1.0.0-dev.2 последний компонент каталога создаётся автоматически, если
родитель существует. `--cache-report` выводит JSON Lines в stderr с готовностью
каталога, попаданиями по imports и check/C, результатами записи и счётчиками
семантической проверки. stdout не меняется. Ошибки каталога и записи видны
также без флага. При этих ошибках компиляция продолжает работать.
Для проверки смотрите `semantic-modules-v1` и поля `declarations_checked`,
`bodies_checked`, `reused_modules`. После правки комментария совпавшие токены
позволяют переиспользовать проверку. В поддержанных графах правка тела или
публичной сигнатуры проверяет затронутые модули.
[Границы переиспользования](contracts/SEMANTIC-CACHE-1.3.md).
Windows-инструмент независимых сборок принимает
1–8 одновременно запущенных корней и сохраняет журналы в каталоге каждого.

```powershell
New-Item -ItemType Directory -Force build/cache | Out-Null
.\vela.cmd run tools/build-batch.vela -- bin/velac.exe build 2 build/cache apps/fielddesk/vela.project apps/source-lens/vela.project
```

Подробнее о ключах, границах и страницах query в
[контракте инкрементальной сборки](contracts/INCREMENTAL-BUILD.md).

## Отладка и профиль

`vela emit-c ROOT --no-ir-simplify` и `vela build ROOT -o OUTPUT --no-ir-simplify`
отключают проход упрощения checked IR для сравнения выдаваемого C. Обе команды
выполняют полную проверку исходников. Для `emit-c` режим совместим с `--debug`.
Анализ диапазонов и отбор функций и типов от точки входа применяются в обоих
режимах. Кэш C хранит результаты упрощения и обхода под разными ключами.
[Упрощение](contracts/IR-SIMPLIFICATION-1.3.md),
[достижимость](contracts/C-REACHABILITY-1.3.md).

### Сборка по профилю

```powershell
New-Item -ItemType Directory -Force build | Out-Null
.\vela.cmd pgo-instrument apps/build-lens/vela.project --profile build/buildlens-pgo
.\vela.cmd pgo-train build/buildlens-pgo -- apps/build-lens/demo.jsonl --top 1
.\vela.cmd build apps/build-lens/vela.project -o build/buildlens-pgo.exe --pgo-profile build/buildlens-pgo
```

Родительский каталог профиля должен существовать. Создавайте новый профиль
для каждого обучения. Устаревший, повреждённый или отсутствующий профиль
даёт E243. Профили поддерживают MSVC 19.44.35222 x64 и GCC 14.2.0
на x86-64 Alpine musl. MCP выполняет изолированную сборку O2.
[Флаги, ограничения и состав профиля](contracts/NATIVE-PGO-1.3.md).

### Оптимизация при линковке

```powershell
.\vela.cmd build apps/build-lens/vela.project -o build/buildlens-lto.exe --lto
```

Чтобы совместить PGO и LTO, добавьте `--lto` к `pgo-instrument` и к итоговому
`build --pgo-profile`. GCC требует профиль, подготовленный в этом режиме.
На MSVC PGO уже включает LTCG и профиль подходит для обоих вариантов.
Чистый LTO на MSVC предпочитает меньший код для коротких функций без
циклов. Такой EXE может выполнять ту же нагрузку дольше обычной сборки.
При неподдерживаемом toolchain обычная сборка остаётся доступна без
`--lto`. [Контракт LTO](contracts/NATIVE-LTO-1.3.md).

### Отладочная сборка

Экспортируйте C с позициями Vela и инструментированием функций.
Команда ниже предполагает консоль разработчика MSVC.

```powershell
.\vela.cmd emit-c tests/tooling/debug.vela --debug -o build/debug.c
cl.exe /nologo /std:c11 /utf-8 /MT /Od /Z7 /Fobuild/debug.obj /Febuild/debug.exe build/debug.c /link /DEBUG:FULL /PDB:build/debug.pdb
$env:VELA_TRACE = '1'
$env:VELA_PROFILE = '1'
.\build\debug.exe
```

Трассировка и профиль идут в stderr. Профиль учитывает время вложенных
вызовов и ожидания внутри async-функции. См. [контракт](contracts/DEBUGGING.md)
и [формат символов MSVC](https://learn.microsoft.com/en-us/cpp/build/reference/z7-zi-zi-debug-information-format).

Формат IR внутренний и пока может меняться. Схема JSON имеет явную версию; несовместимые изменения должны менять `schema_version`.
## Модули и выполнение через MCP

В MCP отдельно включаются vela_build/vela_test/vela_run/vela_read_output. Они используют
проверенную при старте LPAC/Job-песочницу Windows, частный снимок и ограниченный
toolchain. Run принимает выданный artifact_id и параметры запуска. Если backend недоступен,
контекст сообщает execution:false и причину, инструменты анализа остаются доступны.
Это отличается от прямого native CLI с правами пользователя; см.
[контракт выполнения](contracts/MCP-EXECUTION.md).
artifact_id идентифицирует executable. Для отчёта укажите имя в `outputs` и
передайте приложению путь `../export/ИМЯ`. При коде выхода 0 сервер вернёт
метаданные с output_id; клиент получает байты через vela_read_output и сохраняет
их явно после сверки SHA-256. См. [контракт выдачи](contracts/MCP-OUTPUT-ARTIFACTS.md).

check/build/run/symbols/emit-c загружают граф импортов; fmt обрабатывает один файл
или собственные файлы манифеста с --check/--write. test запускает явные test entries.
Контракт команд: [BUILD-PROTOCOL](contracts/BUILD-PROTOCOL.md).
Диагностика сохраняет путь и Unicode-координаты каждого файла. Коды: E221 —
импорт/предел графа; E222 — неоднозначность/alias; E223 — private доступ;
E224 — private тип в public API. Выходной файл не может совпадать с любым
исходником графа по пути или файловой идентичности.

Для проекта с Windows HTTP multi укажите
`native|vela-http.dll|bin/vela-http.dll|windows-x64|1|shared` и обновите lock
после установки DLL. DLL нужна рядом с executable, а для передачи
пакета нужны manifest версий и лицензии. Само приложение открывает адаптер
через `http::curl_multi`. [Сборка и размещение адаптера](contracts/HTTP-MULTI-1.3.md).

# Семантические запросы и правки

`vela query ROOT` возвращает JSON с документами, их ревизиями, определениями,
ссылками, вызовами, типами и эффектами, а также рёбрами импортов.
`--at PATH LINE CHARACTER` ограничивает результат символом в позиции;
строки и UTF-16 колонки начинаются с нуля. `query` и `symbols` работают
и для библиотеки без `main`.

`vela plan ROOT REVISION DOCUMENT BYTE NEW_NAME` проверяет переименование;
`vela plan ROOT REVISION DOCUMENT fmt` готовит правку форматирования.
`vela plan ROOT REVISION DOCUMENT diagnose` объясняет первую ошибку выбранного документа и предлагает только проверенную однозначную правку. Ошибочный JSON-анализ возвращает revision/documents и UTF-16/byte range. `query ROOT --validate` выполняет frontend-check без C/index output; overlays могут включать manifest, parser/lock checks сохраняются. [Контракт](contracts/DIAGNOSTIC-PLANS-1.2.md).
Обе команды возвращают JSON и не записывают исходники. Применять правки
следует к той же версии буфера или к тем же исходным байтам.

`vela-lsp.cmd WORKSPACE [SOURCE_OR_PROJECT]` запускает нативный LSP по stdio:
определения, ссылки, hover, диагностика, переименование и форматирование.
Для переименования откройте все затронутые документы. Протокол и границы:
[запросы](contracts/SEMANTIC-QUERIES.md), [правки](contracts/REFACTORING.md),
[LSP](contracts/LSP.md).
