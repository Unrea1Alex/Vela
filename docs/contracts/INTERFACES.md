# Номинальные интерфейсы — контракты 0.10.4 и 0.10.6

Статическая часть реализована в 0.10.4, явные динамические значения в 0.10.6.

## Идентичность, сигнатуры и реализация

```text
pub interface Reader {
    fn read(self: Self, key: String) -> Result<String, ReadError> effects { io, state };
}
impl Reader for MemoryStore {
    fn read(self: MemoryStore, key: String) -> Result<String, ReadError> effects { state } {
        return lookup(self, key);
    }
}
```

Фрагмент требует объявлений публичного ReadError и
MemoryStore. `interface`, `impl` и `for` здесь распознаются в контексте декларации;
`Self` — placeholder только в interface receiver. Идентичность интерфейса —
модуль-владелец и декларация, а не набор методов или имя. Интерфейс private по
умолчанию; `pub` делает доступными все его сигнатуры. Полей, default bodies,
наследования интерфейсов, generic-интерфейсов/методов, associated types и
пользовательских requires/ensures на interface-операциях в первой версии нет.

`Self` разрешён **только** как тип первого параметра `self`; он запрещён в
остальных параметрах, результате и вложенных типах. Типы остальных параметров
и результата фиксированы и публично доступны для pub-интерфейса. Интерфейс
может не содержать методов; такой bound не даёт новых операций.

Реализацию объявляет **только модуль владельца реализующего номинального типа**.
Он может импортировать чужой публичный интерфейс; владелец интерфейса не может
реализовать его для чужого типа. Для builtin нужен собственный nominal wrapper.
Для пары (Type declaration, Interface declaration) ровно одна реализация во
всём графе; повторный импорт одного файла не создаёт вторую. Нельзя выбирать
реализацию порядком импортов, скрывать конфликт private-декларацией или
специализировать generic-тип. `impl<T> Reader for Store<T>` имеет те же параметры
и bounds, что Store; дополнительные условия запрещены.

В impl нужен каждый метод интерфейса ровно один раз, без лишних методов.
Порядок и типы параметров/результата совпадают после подстановки Self;
имена параметров после self могут отличаться. Эффекты реализации — подмножество
потолка интерфейса. `pub` на impl/его методах и добавочные requires/ensures
запрещены. Доступ следует из доступности интерфейса и типа. Helper-функции и
inherent-методы объявляются отдельно. Это проверка сигнатур, не доказательство
поведенческой эквивалентности: произвольное тело всё ещё может вернуть ошибку
или вызвать panic. Необходимые предусловия описывают результатами API.

## Статический выбор и generics

```text
fn load<T: Reader>(store: T, key: String) -> Result<String, ReadError> effects { io, state } {
    return Reader::read(store, key);
}
```

Interface-вызов всегда имеет явную форму `Reader::read(store, key)` (включая
`api::Reader::read`). Для конкретного типа checker выбирает единственную impl;
для `T: Reader` — обязанность ограничения, разрешаемую при инстанцировании.
При обоих вариантах вызов проверяется по **эффектам интерфейса**, даже если
известная impl требует меньше. Для прямого более узкого API служит отдельный
inherent-метод/функция. Автоматического поиска интерфейсов для `concrete.read()`
нет: эта форма ищет inherent-метод. Два интерфейса с одноимёнными операциями
не создают неоднозначность у явного qualified-вызова.

Один generic-параметр имеет один bound: прежний Any/Scalar/Number либо один
импортированный интерфейс. Пересечения bounds и неявные требования не вводятся.
Наличие методов с подходящими именами без impl недостаточно. Интерфейс не
добавляет арифметические операторы, Scalar-равенство или возможность dict-key.

Тело generic с пользовательским bound проверяется символически до использования:
можно применять лишь операции объявленных ограничений. Это включает все ветви,
contracts/effects и транзитивные generic-вызовы: legacy generic-каллее проверяется
символически в этом контексте, а не считается корректным по одной сигнатуре.
Невыводимая операция — отказ E234, не поиск метода в будущих аргументах.
Рекурсивные obligations кешируются по декларации и символической подстановке;
действующие пределы расширения GENERICS сохраняются, превышение — E217.
После подстановки остаётся конкретная проверка layout/тела перед C.

Существующие generic без пользовательских bounds сохраняют отложенную проверку
при инстанцировании. В 0.10.4 query получает аддитивное поле schema 1
`analysis_status`: у function definitions обычной Vela-функции с проверенным
телом — `checked_body`,
legacy-шаблон — `deferred`, шаблон с interface-bound — `checked_constraints`.
Статус **шаблона** не меняется от наличия конкретных вызовов. У `role: call`
проверенная конкретная generic-специализация имеет `checked_instance`, обычная
Vela-цель с проверенным телом — `checked_body`; остаются конкретные type/effects
ссылки. У extern definitions и у вызовов builtin/extern/абстрактной interface-
операции без выбранного проверенного Vela-тела поле отсутствует: проверка
сигнатуры не выдаётся за проверку реализации. Отсутствие поля не эквивалентно
`checked_body`. Поэтому даже один
source ID может иметь deferred-определение и checked_instance-вызовы с разными
типами. Пустые поля deferred не означают проверенную чистоту. Для других kinds/
roles поле не добавляется; недостоверные binding-факты ошибочного графа не
дополняются выдуманными статусами.

## Явные динамические значения (0.10.6)

```text
let reader: dyn Reader = dyn Reader(store);
let answer = reader.read("settings");
```

`dyn Reader` — самостоятельный номинальный тип; `dyn Reader(value)` — явная
упаковка типа с проверенной impl. Неявное преобразование T → dyn Reader,
перепаковка dyn Reader в другой интерфейс, downcast, Any и equality запрещены.
`dyn Reader` не имеет собственной impl Reader и не удовлетворяет bound
`T: Reader`: для dynamic-пути функция принимает `dyn Reader` явно. `reader.read`
и `Reader::read(reader, key)` обращаются к одной известной таблице; эффекты в
обоих случаях берутся из Reader. Другие сигнатуры первой версии не object-safe.

Упаковка вычисляет value один раз, делает shallow-copy и создаёт **один**
управляемый box с payload конкретного типа. Box immutable; копия оболочки
разделяет box. Каждый вызов получает shallow-copy payload как self, точно как
статический путь. Общие List/Dict/ForeignHandle сохраняют идентичность; локальная
скалярная мутация self не меняет box. Повторная явная упаковка создаёт другой box,
но вложенные handles всё ещё могут быть общими. Скрытого close при копировании,
замене, уничтожении оболочки или сборке box нет.

Оболочка хранит managed box pointer и указатель на immutable таблицу конкретной
impl; таблица и код живут до завершения процесса. Точные offsets C остаются
внутренними, не FFI ABI. Статическая проверка выбирает таблицу; runtime не
проводит поиск по строкам/типам. Descriptor box трассирует все поля payload,
включая скрытые; оболочки, временные значения и извлечённый self имеют roots.
Циклы через коллекции освобождаются при недостижимости. Никаких ссылок на стек
или на элементы изменяемых буферов наружу не выходит.

Close общего ForeignHandle инвалидирует его во всех boxes/closures/копиях.
Закрытая metadata может оставаться достижимой; её GC-root не открывает ресурс.
Повторный close/вызов после close сохраняет правила FFI-ROOTS/FFI. Dynamic-вызов
сам по себе не закрывает ресурс и не обещает, что произвольный объект closeable.
Операция close должна быть явно объявлена в нужном интерфейсе с обычным результатом.

Ошибки: E234 для отсутствующего bound/недоступной операции; E235 для владельца
или неоднозначной impl; E236 для состава/сигнатуры/эффектов impl; E237 для
недопустимой dynamic-формы; E209 для недостаточных эффектов вызывающего кода.
FFI ABI 1 не принимает interface/callable values даже при известном layout.

Checker разрешает операции по порядку декларации интерфейса и записывает
индекс операции в проверенном вызове. Таблица создаётся один раз на пару
конкретный тип и интерфейс. Её адаптеры загружают копию payload, а затем
передают её обычной Vela-функции с уже проверенной сигнатурой.
Оба синтаксиса вызова сначала вычисляют получателя, затем остальные аргументы
слева направо. В generic-теле упаковка `dyn Reader(value)` разрешается для
`T: Reader`, а конкретную таблицу выбирает специализация. Конверсия с
динамического значения, включая уже упакованное `dyn Reader`, отклоняется.

Приёмка использует выбор между двумя реализациями во время исполнения,
одинаковые успешные и ошибочные результаты статического и динамического
путей, общий список из закрытого payload и цикл со списком динамических
значений. Проверка сборки циклов сравнивает объём управляемой памяти при
одинаковом наборе живых объектов. Проверка времени, размеров C и executable
следует [заранее заданным бюджетам](ABSTRACTIONS-VALIDATION.md).
