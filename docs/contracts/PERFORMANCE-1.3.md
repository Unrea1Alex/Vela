# Протокол измерений Vela 1.3

Зафиксировано для 1.3.1 перед изменениями std, runtime и компилятора.
Исходная ревизия `606ee55`, компилятор Vela 1.2.0. Эксперимент проводится на
одной Windows x64 машине с обычной оптимизированной сборкой Vela/MSVC.
Эта серия измерений выполняется отдельно от независимого VelaBench в 1.4.6.

| Задача | Small / medium / large | Эталон результата |
| --- | --- | --- |
| Повторный поиск в Config | 8 / 64 / 256 ключей, 2000 поисков последнего ключа | 2000 успешных чтений со значением `7` |
| Text и Path | UTF-8 путь с 64 / 1024 / 8192 ASCII байтами, 2000 операций | 2000 корректных срезов / parent |
| JSON tree, stream skip, typed decode | 8 / 64 / 256 ключей, 300 документов | Принятие всех документов, typed поле `target=7` |
| Строки и копирование | 64 / 1024 / 8192 байта, 4000 срезов/конкатенаций | 4000 длин, совпадающих с ожидаемой |
| Агрегация, Set, Cell | 128 / 2048 / 16384 элементов, 12 проходов | Сумма 1..N, N ключей без повторов, N инкрементов |
| Native Reader/Writer | 256 KiB / 2 MiB / 16 MiB, буфер 16 KiB | Точное совпадение SHA-256 входа и выхода |
| HTTP helper | 1 / 4 / 10 GET последовательных, loopback HTTP/1.1, ответ 64 байта | Статус 200, 64 байта, порядок; счётчик серверных соединений |
| Компилятор | Копия всех authored selfhost модулей и embedded, cold/warm/edit | Успешный check, miss/hit/miss, после комментария тот же результат |

Для каждой нагрузки один разогрев и пять измеряемых запусков, последовательно.
Cold означает новый каталог кэша Vela; кэш файлов ОС остаётся включённым.
Файловый вывод очищается перед следующим замером. HTTP сервер находится вне
измеряемого дерева, новый счётчик используется для каждого процесса. Отдельно
измеряется обычная сборка приложения BuildLens (со своими C compiler children).
В отчёте хранятся исходные замеры, медиана и диапазон без удаления выбросов.
Wall, CPU и peak private commit всего дерева измеряет ранее проверенный
Windows Job ProcessMeter из VelaBench. Пик managed heap, число GC и счётчики
выделений/копирования собираются в отдельном запуске. Для счётчиков runtime
инструментируется копия emitted C; её время не используется в сравнении.
Счётчики `memcpy` учитывают явные вызовы после вставки обёртки в runtime C.
Копирования, выполняемые компилятором C, ОС или C-библиотекой, вне этого счётчика.
Линейные проверки Text/Path/Config дополнительно считаются по числу вызовов
публичных операций и по структуре вызываемого кода.

До оптимизации выбираются основные цели по медиане wall: минимум **20%**
на medium repeated Config lookup, Text/Path (по отдельности), последовательном
HTTP из 10 запросов и комментарии в копии selfhost. Для 1.3.4 выбрать горячую
операцию по baseline JSON/строк/агрегации и записать выбор до изменения кода.
Каждое сравнение повторяет вход, число операций, oracle и toolchain. Для
Text/Path учитывается первая проверка и все последующие чтения, для Config
построение снимка и все поиски. Дополнительные размеры показывают цену
начальной работы и масштабирование. Пик commit и размер пакета имеют бюджет
до **+10%**. Для выхода за него требуется отдельное решение с обоснованием.
Функциональные регрессии и ослабление проверок недопустимы.
