## 1. Назначение и приоритеты

Vela развивается как компилируемый язык общего назначения. Первые пользователи
его возможностей — собственный компилятор, инструменты разработки, обработка
данных и автоматизация. До 1.0 должна быть проверена пригодность и для обычных
приложений: графический интерфейс, сеть, длительная работа и поставка пользователям.

«Удобен мне» означает, что агент может понять и изменить небольшой участок кода,
опираясь на явные интерфейсы и ответы компилятора. Приоритеты:

1. Локальная понятность: явные типы, зависимости, эффекты и правила владения ресурсами.
2. Предотвращение ошибок: номинальные ID, исчерпывающие варианты, проверка до backend.
3. Короткий цикл «изменение → проверка → исправление», машинно-читаемые результаты.
4. Предсказуемые вычисления, контролируемые внешние действия, воспроизводимые тесты.
5. Умеренная сложность языка: новая возможность должна решать наблюдаемую задачу.

C остаётся основным backend как минимум до 1.0. Переход к LLVM/WASM или другому
backend рассматривается по измеренным потребностям. Компилятор, разработческие
инструменты и обычный цикл проверки остаются на Vela, без зависимости от Python.
Узкое исключение для внешней MCP-интеграции: адаптер транспорта,
доступа к справке и запуска процессов — TypeScript/Node.js с официальным MCP SDK.
Алгоритмы языка остаются в нативном компиляторе; Node.js и MCP не входят
в зависимости сборки, bootstrap, native verify или запуска обычных Vela-программ.

## 2. Зафиксированная база

0.3 включает структуры, distinct-ID, List<T>, Dict<K,V>, соединение строк,
самокомпилятор, нативные bundler/dev/test и общий каталог builtin.

По сохранённым отчётам: 199 нативных проверок, 0 ошибок, 0 пропусков; сходимость
компилятора и сборщика; проверка нативной поставки без Python и восстановления из C.
Это база отчётов 0.3, а не новый прогон при написании плана:

- [Архитектура](ARCHITECTURE.md), [язык](LANGUAGE.md), [память](MEMORY.md).
- [Bootstrap](bootstrap-evidence.json), [тесты](test-evidence.json),
  [поставка](delivery-evidence.json), [условия проверки](VALIDATION.md).
- [Компилятор и внутренние записи](../selfhost/README.md).

В 0.8 доступны точная трассировка памяти, лексическая очистка и синхронный
Windows x64 FFI ABI 1 с явными корнями. ID остаются локальными для Context.
0.9 добавляет нативный LSP и планы правок. В 0.10 реализованы функции/замыкания,
интерфейсы, подменяемые сервисы, replay и callbacks; проверены приложения с Win32 GUI.
В 0.11 проверены typed async, HTTP/HTTPS на Windows, loopback-сервер и кэш
проверки/экспорта C. В серии 1.0.0-dev появились awaitable HTTP/process и общий
Windows GUI-слой. Переносимый GUI и частичный пересчёт семантики между изменениями
графа пока не реализованы. Старый Windows HTTP-прототип остаётся
историческим примером; актуальный клиент — `std/http.vela`.

## 4. Порядок выполнения каждого пункта

1. **Уточнить границы.** Выбрать ID пункта, прочитать связанные спецификации,
   записать его статус «В работе», ограничения и нерешённые вопросы.
2. **Определить контракт до реализации.** Зафиксировать наблюдаемую семантику,
   инварианты, ошибки, эффекты, время жизни и совместимость. Для существенного
   решения сначала написать RFC; простой пункт может ссылаться на существующий контракт.
3. **Определить доказательство готовности.** Указать положительные, отрицательные
   и граничные сценарии. Ожидаемые результаты выводятся из контракта.
4. **Реализовать небольшой законченный блок.** Сохранять границы фаз, не поручать
   проверку языка C-компилятору. Отдельно выполнить миграцию собственного кода.
5. **Проверить блок сразу.** Запустить относящиеся к нему тесты; исправить ошибки
   до продолжения зависимой работы. Временно реализованное без проверки отметить
   явно, не закрывать пункт.
6. **Обновить действующую документацию.** Спецификация языка/API, архитектура,
   память, протоколы, примеры и миграция должны соответствовать фактическому коду.
7. **Выполнить общий gate по масштабу изменения.** Изменения compiler/runtime
   требуют `.\vela-dev.cmd verify`; изменения tools — проверки соответствующего
   инструмента и интеграционного цикла. Перед выпуском — полный gate ниже.
8. **Обновить этот файл в том же изменении.** Указать статус, доказательства,
   оставшиеся ограничения, изменённые зависимости и следующий пункт.

Проверки самого изменения документации: целостность ссылок, порядок зависимостей,
отсутствие противоречий и ясное разделение «есть/планируется». Изменение только
документации не требует компиляции или повторения всей runtime-матрицы, кроме
явно заказанного gate каждого этапа 1.1–1.10 ниже. Само редактирование этого плана
не является выполнением этапа и проверяется как документационное изменение.

### Что должно быть в контракте

Контракт здесь — спецификация поведения/API/представления. Это не обещание
статически доказать `requires/ensures`: пользовательские контракты пока runtime.

Для нового или изменённого интерфейса записывать применимые пункты:

- Назначение, область действия, входы/выходы, типы и правила вывода.

#### Протокол итогового VelaBench в 1.4.6

- **Независимость:** те же 3 задачи, Vela/Rust/Go, по 3 свежие сессии — 27 попыток;
  затем 27 продолжений собственной сессии для исходного maintenance-задания.
  Без общей памяти, соседних решений и обратной связи скрытого evaluator.
  Изоляция описывается фактически, без заявления OS sandbox при одном запрете
  в инструкции. Код участников исследователь не исправляет.
- **Сопоставимость:** исходные задания/лимиты/oracle и порядок приёмки не
  облегчаются. Исходный минимум: model `gpt-6.1-sol`, medium, 15 минут на фазу,
  зафиксированные Rust/Go версии; доступная актуальная модель не подставляется
  молча. При недоступности старой среды провести новую согласованную контрольную
  серию на сохранённой Vela 1.0 и той же модели/инструментах, а историческую базу
  показать отдельно. Продолжения не считать новыми независимыми реализациями.
- **Корректность:** отдельный независимый oracle и холодная пересборка каждой
  сдачи. Проверять свежий output каждого запуска, точное число HTTP-запросов,
  concurrency, deadline, повторное чтение и сохранение результата при ошибке.
  Только полные проходы допускаются к сравнению производительности; затраты
  неуспешных попыток входят в итоговый расход. Любое изменение SDK участником
  сохраняется как результат, но не удовлетворяет цели штатной библиотеки.
- **Метрики агента:** wall time, время до первого успешного build/test (по
  событиям, иначе N/A), input, cached input, uncached input, output и reasoning,
  число инструментов/обращений к справке/ошибочных команд/исправительных циклов.
  Накопленные counters продолжения нормализуются вычитанием исходной фазы;
  cached и reasoning не прибавляются повторно. Оценки понимания, выражения,
  диагностики, изменяемости и уверенности 1–5 собираются до внешних результатов.
- **Метрики программ:** wall/CPU всего дерева, peak private commit и отдельно
  рабочий набор родителя, startup, small/medium/large, HTTP single/batch,
  throughput, median/p95/интервалы, cold/warm/edit build, EXE и пакет с
  библиотеками/помощниками. По 20 обычных запусков, 100 HTTP single, warmup
  отдельно; артефакты чередуются с фиксированным seed, во время измерений нет
  работающих агентов. Относить данные к хешу реально проверенного EXE.
- **Длительная работа:** сохранить исходные 200 повторов в одном процессе;
  дополнительно зафиксировать более ёмкий одинаковый сценарий, если ряд слишком
  короткий. Для сравнения квартилей минимум 8 пригодных отсчётов и 250 ms
  наблюдения; иначе N/A. Новый soak помечается отдельно от исторического.
  Проверять запросы/handles/cleanup; изменение commit само по себе не доказывает
  утечку и не заменяет проверку удерживаемых ресурсов.
- **Интерпретация:** сначала correctness, затем стоимость успешного решения и
  метрики на одинаковых задачах; не усреднять разные наборы принятых задач как
  общий рейтинг. Отдельно сравнить Vela 1.0/1.4 и Vela/Rust/Go. Полные расходы
  контекста, некэшированные токены и длина исходника — разные показатели;
  деньги не вычисляются без фактического тарифа. Предобучение модели и качество
  библиотек входят в практический результат, причинный эффект синтаксиса не доказан.
- **Выход:** HTML с фильтрами, исходные CSV/JSON, промпты, логи, self-assessments,
  снимки SDK/исходников/EXE, зависимости, fingerprints и воспроизводимые команды.
  Проверить данные, ссылки/скрипты и визуально открыть отчёт доступным разрешённым
  способом; непроведённую клиентскую/визуальную проверку отметить явно.
  Итог включает достигнутые/недостигнутые цели, диапазоны при n=3 и конкретные
  следующие работы. Новые проверки вне исходных заданий публикуются отдельно.

**Порядок и границы.** 1.5.1 зависит от принятой 1.4.6; следующие версии и пункты
выполняются строго по порядку. Общий gate каждого этапа выше обязателен:
фокусная проверка + **`.\vela-dev.cmd verify` после каждого пункта**, включая
дизайн, документацию и приёмку. Невыполненный критерий оставляет пункт открытым.
Старые native/bootstrap, GUI/network и VelaBench обязательства сохраняются.

До реализации каждого нового механизма оформляется действующий контракт после
принятия дизайна: эффекты, ошибки, пределы, ownership, GC/FFI, отмена/close,
форматы и миграции, платформы. Предлагаемые имена библиотек и API уточняются там.
Компиляция Vela, проверка описаний схем и типов запросов, генерация и анализ
остаются на Vela; native примитивы обслуживают ОС/вызовы библиотек, включая
хранение и исполнение SQL движком SQLite. SQLite в 1.5 подключается через
узкие примитивы хранения, не ожидая расширенного публичного FFI из 1.9.3.
Обычная native сборка не получает зависимость от Python, Node.js или registry.

**Совместимость.** Все дополнения 1.x включаются явно, сохраняют рабочий старый
код/форматы и публичный ABI 1. Новые ограничения владения не применяются молча к
старым List/Dict/handles. Изменение формата на диске требует версии, миграции и
отказа при неизвестной версии. Если совместимый дизайн невозможен, реализация
блокируется до пересмотра контракта либо явного переноса в major-версию с причиной
в roadmap; обещание не исчезает. Runtime `requires/ensures` остаются проверками.

**Платформы.** Данные и синхронные консольные библиотеки 1.5 проверяются на
Windows x64 и Linux x86-64. Новые сервер/асинхронные workers до 1.9.5 проходят
Windows-матрицу, остальные платформы явно маркируются unsupported; это не
объявление готовности Linux-сети. В 1.9.5 обе платформы получают обязательную
матрицу данных/сети/workers. В 1.10.3–1.10.5 отдельно принимается GUI на обеих ОС.

#### Протокол передачи приложений в 1.10.6

1. **Агент A создаёт.** Для каждого из трёх приложений отдельная новая сессия
   получает нейтральный функциональный prompt, выпущенный SDK/docs/skill и
   разрешённые инструменты. Нет доступа к эталонному приложению, соседям или
   закрытым тестам. Исторические проекты служат исследователю fixtures, а не
   выдаются как готовая реализация. Источник, зависимости и EXE замораживаются.
2. **Агент B расширяет.** Новый контекст получает только проект A и его
   документацию, без истории чата. Заранее фиксируются изменения: для DocBase —
   новое сохраняемое поле/фильтр с миграцией, для JobQueue — новая политика
   исполнения с совместимостью активных jobs, для DataPipe — новое преобразование
   с сохранением streaming/budgets. Проверяются новые и все прежние сценарии.
3. **Агент C исправляет.** Новый контекст получает копию изменённого проекта
   с заранее подготовленным воспроизводимым дефектом и наблюдаемым симптомом.
   Исходная исправная сдача хранится отдельно. Дефект миграции/отмены/границ
   streaming должен нарушать независимый тест; исправление не меняет его oracle.
4. **Независимый evaluator принимает.** Минимум одна цепочка A→B→C на приложение,
   всего минимум 9 сессий; следующий handoff начинается только после приёмки
   предыдущего. Неуспешный handoff не заменяется удачным в том же отчёте;
   исправление среды/SDK требует новой помеченной серии. Кандидат Vela и модель,
   effort, лимиты, платформы и задания фиксируются до сессий.
5. **Результаты сохраняются.** В каждой фазе: корректность, независимая сборка,
   runtime/resources/size, время агента, input/cached/output/reasoning без
   двойного счёта, обращения к справке, исправительные циклы, объём изменений,
   самооценки с доказательствами. Отдельно показать обнаруженные последствия,
   требуемые миграции и пропущенные зависимости. Выпустить HTML/CSV/JSON со всеми
   сессиями и snapshot/hash/логами; малую выборку не выдавать за общий рейтинг.
