## 1. Назначение и приоритеты

Vela развивается как компилируемый язык общего назначения. Первые пользователи
его возможностей — собственный компилятор, инструменты разработки, обработка
данных и автоматизация. До 1.0 должна быть проверена пригодность и для обычных
приложений: графический интерфейс, сеть, длительная работа и поставка пользователям.

«Удобен мне» означает, что агент может понять и изменить небольшой участок кода,
опираясь на явные интерфейсы и ответы компилятора. Приоритеты:

1. Локальная понятность: явные типы, зависимости, эффекты и правила владения ресурсами.
2. Предотвращение ошибок: номинальные ID, исчерпывающие варианты, проверка до backend.
3. Короткий цикл «изменение → проверка → исправление», машинно-читаемые результаты.
4. Предсказуемые вычисления, контролируемые внешние действия, воспроизводимые тесты.
5. Умеренная сложность языка: новая возможность должна решать наблюдаемую задачу.

C остаётся основным backend как минимум до 1.0. Переход к LLVM/WASM или другому
backend рассматривается по измеренным потребностям. Компилятор, разработческие
инструменты и обычный цикл проверки остаются на Vela, без зависимости от Python.
Узкое исключение для внешней MCP-интеграции: адаптер транспорта,
доступа к справке и запуска процессов — TypeScript/Node.js с официальным MCP SDK.
Алгоритмы языка остаются в нативном компиляторе; Node.js и MCP не входят
в зависимости сборки, bootstrap, native verify или запуска обычных Vela-программ.

## 2. Зафиксированная база

0.3 включает структуры, distinct-ID, List<T>, Dict<K,V>, соединение строк,
самокомпилятор, нативные bundler/dev/test и общий каталог builtin.

По сохранённым отчётам: 199 нативных проверок, 0 ошибок, 0 пропусков; сходимость
компилятора и сборщика; проверка нативной поставки без Python и восстановления из C.
Это база отчётов 0.3, а не новый прогон при написании плана:

- [Архитектура](ARCHITECTURE.md), [язык](LANGUAGE.md), [память](MEMORY.md).
- [Bootstrap](bootstrap-evidence.json), [тесты](test-evidence.json),
  [поставка](delivery-evidence.json), [условия проверки](VALIDATION.md).
- [Компилятор и внутренние записи](../selfhost/README.md).

Ограничения исторической базы 0.3 включали отсутствие публичного FFI.
В текущей 0.7.0 реализован синхронный Windows x64 FFI ABI 1, есть ограниченные
GUI/HTTP прототипы. Сохраняются процессная область памяти, ID в одном Context,
отсутствие GC, функций как значений, полноценного GUI/network API, асинхронных
задач, LSP и инкрементальной проверки. Прототипы не заменяют будущие framework gates.

Документирование будущей архитектуры допустимо раньше реализации, но не означает
готовность функции и не меняет действующую спецификацию языка.

Критические зависимости:

- Контракты типов/ID → миграция AST/HIR → последующие изменения checker/backend.
- Generics и Result/Option → модульные публичные интерфейсы → расширенная библиотека.
- Модули и проектная сборка → подключение внешних библиотек и их упаковка.
- Проект модели памяти и FFI согласуется до их реализации; GC появляется до
  постоянного сервера анализа, удерживаемых замыканий и долгоживущих GUI-объектов.
- Контракт callable/effects из 0.5 → функции/замыкания и callbacks в 0.10.
- FFI + ресурсы + callbacks → GUI; цикл событий + отмена → отзывчивый сетевой GUI.
- Сеть и GUI не становятся зависимостями bootstrap-компилятора без необходимости.
- Проектный формат и CLI 0.6.1–0.6.5 → контракт MCP 0.6.6 → адаптер 0.6.7 →
  поставка и проверка нового агента 0.6.8. Первый MCP использует отдельный процесс
  компилятора на запрос и не требует постоянного Vela-сервиса или GC.
- MCP 0.6.8 + файловые/process API и тесты 0.7.2–0.7.3 → контракт выполнения
  0.7.7 → сборка/тесты/изолированный запуск 0.7.8. Тайм-аут, эффекты Vela и
  рабочая папка не заменяют ОС-изоляцию исполняемой программы.
- GC/ресурсы 0.8 и сервис анализа 0.9.1–0.9.5 → семантический MCP 0.9.6.
  Перенос постоянного адаптера на Vela требует отдельного решения и проверки памяти.
- Проверка памяти/ресурсов 0.8.1–0.8.6 → прикладные дополнения 0.8.7–0.8.10:
  математика, формат чисел, JSON-извлечение и builder с определённым временем жизни.
- Текстовые API 0.8.10 и граф/lock проекта → текстовые литералы/ресурсы 0.9.7 →
  форматирование этих конструкций 0.9.8. MCP execution 0.7.8 и правила ресурсов →
  выдача созданных файлов 0.9.9; она не зависит от решения о переносе адаптера на Vela.

При появлении новой зависимости сначала исправить порядок и причины в плане.
Текущее явное поручение пользователя имеет приоритет над порядком дорожной карты.

## 4. Порядок выполнения каждого пункта

1. **Уточнить границы.** Выбрать ID пункта, прочитать связанные спецификации,
   записать его статус «В работе», ограничения и нерешённые вопросы.
2. **Определить контракт до реализации.** Зафиксировать наблюдаемую семантику,
   инварианты, ошибки, эффекты, время жизни и совместимость. Для существенного
   решения сначала написать RFC; простой пункт может ссылаться на существующий контракт.
3. **Определить доказательство готовности.** Указать положительные, отрицательные
   и граничные сценарии. Ожидаемые результаты выводятся из контракта.
4. **Реализовать небольшой законченный блок.** Сохранять границы фаз, не поручать
   проверку языка C-компилятору. Отдельно выполнить миграцию собственного кода.
5. **Проверить блок сразу.** Запустить относящиеся к нему тесты; исправить ошибки
   до продолжения зависимой работы. Временно реализованное без проверки отметить
   явно, не закрывать пункт.
6. **Обновить действующую документацию.** Спецификация языка/API, архитектура,
   память, протоколы, примеры и миграция должны соответствовать фактическому коду.
7. **Выполнить общий gate по масштабу изменения.** Изменения compiler/runtime
   требуют `.\vela-dev.cmd verify`; изменения tools — проверки соответствующего
   инструмента и интеграционного цикла. Перед выпуском — полный gate ниже.
8. **Обновить этот файл в том же изменении.** Указать статус, доказательства,
   оставшиеся ограничения, изменённые зависимости и следующий пункт.

Проверки самого изменения документации: целостность ссылок, порядок зависимостей,
отсутствие противоречий и ясное разделение «есть/планируется». Изменение только
документации не требует компиляции или повторения всей runtime-матрицы.

### Что должно быть в контракте

Контракт здесь — спецификация поведения/API/представления. Это не обещание
статически доказать `requires/ensures`: пользовательские контракты пока runtime.

Для нового или изменённого интерфейса записывать применимые пункты:

- Назначение, область действия, входы/выходы, типы и правила вывода.
- Предусловия, постусловия, инварианты; корректные и запрещённые примеры.
- Порядок вычисления, мутация, aliasing, эффекты и наблюдаемое поведение.
- Владение, время жизни, освобождение, копирование, взаимодействие с GC/FFI.
- Ошибки, Result/диагностики/коды завершения; состояние данных после отказа.
- Для асинхронности: поток исполнения, reentrancy, отмена, тайм-аут, завершение,
  поведение при закрытии владельца и порядок освобождения ресурсов.
- Детерминизм, числовые/размерные ограничения, платформенные различия.
- ABI/schema/version, совместимость bootstrap-поколений и миграция старого кода.
- Наблюдаемые критерии приёмки и ссылки на проверяющие их тесты.

Существенные предложения хранить в `docs/rfcs/NNNN-topic.md` со статусами
«Предложено / Принято / Заменено». Принятые действующие контракты — в
`docs/contracts/TOPIC.md` или соответствующей существующей спецификации.
Эти каталоги и тематические документы создаются по мере работы; перечисленные
ниже будущие документы пока не считаются существующими или утверждёнными.
Решение о дизайне фиксируется с обоснованием; обычные решения в уже порученной
работе не требуют отдельного запроса разрешения пользователю.

обслуживает несколько соединений. Поставка запускается вне рабочего проекта.

Удалённый MCP через Streamable HTTP — отдельный кандидат после локальной приёмки
0.6/0.7 и сетевых контрактов 0.11. До реализации нужны явная потребность,
контракт аутентификации/доступа, изоляции проектов, отмены/квот и поставки.
Он не входит в локальный MVP и не объявляется поддержанным от наличия HTTP.

переводит пункты реализации в состояние «В работе».

- Обновить пункт и статус версии; для частичной готовности описать, что осталось.

  проверок и относительные пути доказательств.

- При перестановке или переносе сохранить причину и последствия; не удалять
  невыполненные обязательства, создавая видимость завершения.
