# Исходный профиль Vela 1.3

## Контроль генерации C после 1.3.4d

Две серии повторяют один и тот же принятый компилятор после аудита. В каждой
группе пять пар после разогрева. Корпус включает 30 групп для Windows и 28 для
Linux. [Контракт и критерии](contracts/C-OPTIMIZATION-1.3.md) ·
[MSVC, сырые данные](acceptance/1.3.4e-msvc.json) ·
[GCC, сырые данные](acceptance/1.3.4e-gcc.json).

| Нагрузка, медиана wall | MSVC x64 | GCC x86-64 |
|---|---:|---:|
| Большой числовой цикл | 25,53 мс | 5,26 мс |
| Большой скалярный агрегат | 51,84 мс | 30,59 мс |
| Typed JSON, 64 ключа | 67,18 мс | 64,16 мс |
| BuildLens, 10 000 событий | 341,24 мс | 490,17 мс |
| FieldDesk, demo с replay | 40,59 мс | 35,76 мс |
| Самокомпиляция, frontend и запись C | 1,76 с | 2,51 с |
| Самокомпиляция, отдельный C compile/link | 38,16 с | 52,54 с |
| Самокомпиляция, полная сборка | 40,44 с | 55,12 с |

Обе версии C компилятора содержат 21 920 вызовов регистрации roots, 29 961
poll, 716 проверяемых арифметических вызовов, 39 698 временных объявлений,
517 определений функций и 68 типов по счётчику генерации. На большой нагрузке
скалярных агрегатов медианная абсолютная разница пары равна 2,62% на MSVC и
0,56% на GCC. Для большого числового цикла это 5,92% и 4,44% соответственно.
Порог сравнения рассчитывается отдельно для каждой нагрузки.

Полная самосборка имела медианный peak Job commit 750 MiB на Windows и
наблюдаемый peak RSS дерева 602 MiB на Linux. Linux-метрика использует выборки
изолированной сессии и отдельный максимум `wait4`. Архив компилятора из
измерительного корпуса занимает 2 649 314 и 3 289 360 байт соответственно.
Это фиксированный измерительный состав, а финальная поставка проверяется в 1.3.6.

### 1.3.4f, корни скалярных агрегатов

В изолированном скалярном fixture осталось 5 из 21 регистрации корня и 10 из
14 обходчиков. Смешанный fixture сохранил 33 регистрации и 13 обходчиков.
В корпусе компилятора число регистраций уменьшилось с 21 920 до 19 072.

| Нагрузка, wall median | MSVC, парный контроль → кандидат | GCC, парный контроль → кандидат |
|---|---:|---:|
| Большой скалярный агрегат | 52,63 → 34,24 мс | 31,52 → 5,87 мс |
| Сборка фиксированного selfhost | 40,09 → 34,50 с | 55,28 → 53,26 с |

В обеих сериях уложились в пределы по wall, CPU, памяти и архиву. Оба
компилятора в каждой паре собирали один зафиксированный исходник 1.3.4d.
У перенесённого selfhost меняются байты пути в диагностике. Восстановление
актуального 1.3.4f проверяется из его собственного C отдельно.
[MSVC](acceptance/1.3.4f-msvc.json) · [GCC](acceptance/1.3.4f-gcc.json).

снизилась с 2 603,53 до 1 337,45 мс на GCC и с 1 069,11 до 589,48 мс на

решения по каждой правке, копирование, аллокации и пределы сравнения с
историей 1.2.8a. [Аудит](COMPILER-AUDIT-1.3.md#compiler-costs-and-build-dependencies-135a).

1 398,68 → 751,74 мс cold, 144,70 → 110,42 мс warm и 1 337,88 → 117,08 мс
после комментария. Выигрыш edit 91,25%, повторно проверено ноль тел из 32.

HTTP-запроса. Первый вариант драйвера активно опрашивал завершённый пул
между turns приложения, расходуя около 328 мс CPU в серии из десяти GET.
Ожидание готовности сокета и краткая пауза при пустом пуле снизили расход
CPU. Отдельный тест с дедлайном 50 мс сохранил исходный порог.

EXE HTTP Collector вырос с 1 107 968 до 1 121 280 байт. Опциональная Windows
DLL занимает ещё 4 363 776 байт до сжатия. Пакет приложений выходит за
бюджет +10% относительно прежней поставки с системным curl. Выбор для
сетевого пакета — статические libcurl/OpenSSL/c-ares в одной DLL, с
изолированными CA и асинхронным DNS. Это устраняет зависимость от версии
системного curl и позволяет доставлять обновления TLS вместе с приложением.
Обычные console-программы и bootstrap не требуют DLL. Размер итогового SDK
и окончательный баланс поставки проверяются отдельно в 1.3.6.
