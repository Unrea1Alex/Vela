# RFC 0004 — абстракции данных и поведения, эффекты

Дата: 2026-11-05. Статус: **направление включено в план; контракты и синтаксис
ещё не приняты, реализация не начата**. Пункты: [roadmap 0.10.1–0.10.11](../ROADMAP.md).
Рабочая версия остаётся 0.7.0; следующий этап разработки — 0.8.1.
Документ не расширяет [действующий язык](../LANGUAGE.md).

## Потребность

Для compiler/tools и MeasureLab хватило структур, enum, generics и функций модулей.
Для библиотек и GUI нужны дополнительные гарантии: клиент не нарушает инварианты
данных прямой записью, один алгоритм работает с несколькими реализациями сервиса,
а передача поведения не скрывает эффекты и время жизни ресурсов.

Сейчас [модули](../contracts/MODULES.md) скрывают объявления, но поля и варианты
публичного типа открыты. [Generics](../contracts/GENERICS.md) имеют ограниченный
набор bounds и не позволяют потребовать пользовательскую операцию у типа.
Методы, интерфейсы поведения, функции как значения и замыкания не реализованы.
Эффекты — только io, args, state и process; любой extern требует process/state.

Необходимая основа — инкапсуляция, явные контракты поведения и сохранение эффектов.
Методы полезны для организации API и обнаружения операций инструментами.
Динамический выбор нужен там, где реализация определяется при запуске и хранится
как зависимость приложения; обычным generic-алгоритмам остаётся статический путь.
Наследование реализации для этих задач не требуется.

## Принцип первой реализации

Данные собираются композицией структур. Доступ к скрытой части контролирует модуль
владельца; реализация интерфейса объявляется явно, совпадение имён само по себе
не создаёт совместимость. Статический и динамический выбор различимы в программе.
Название будущей конструкции (interface/protocol/trait) выбирается в 0.10.1;
термин «интерфейс» здесь не является новым ключевым словом.

| Средство | Обязательный результат | Граница первой версии |
|---|---|---|
| Закрытое представление | Публичный тип со скрытыми полями и контролируемым конструированием | Существующие открытые структуры не становятся закрытыми автоматически |
| Методы | Операции типа с явным receiver, доступные поиску и переименованию | Один владелец, без перегрузки и extension methods чужих типов |
| Статические интерфейсы | Общий алгоритм вызывает только операции объявленного ограничения | Явная реализация; без специализации, associated types и наследования реализаций |
| Callables/замыкания | Передаваемое поведение с сохранением типов, эффектов и захватов | По [RFC 0002](0002-generics-callables.md), после проверки памяти/ресурсов |
| Интерфейсные значения | Выбор реализации во время выполнения и хранение её в приложении | Явная упаковка; без Any, автоматического downcast или неявного boxing |
| Подменяемые зависимости | Один клиент использует настоящий либо тестовый сервис | Явная передача; без глобального неявного поиска сервисов |

## Что обязательно решить до реализации

**Инкапсуляция.** Установить область доступа, допустимое публичное конструирование
и обновление, представление opaque-типа и правила скрытых private-типов. Ограничения
должны работать через imports, generics, методы и интерфейсы. Публичные сигнатуры
и открытые поля не могут выдавать private-типы. Совместимость здесь означает
пересборку клиентского исходника, а не обещание стабильного бинарного layout.
Изменение внутреннего представления должно инвалидировать затронутые сборочные кэши.

**Receiver и состояние.** Сохранить различие копируемой структуры и общей
изменяемой коллекции. Описать чтение, передачу, изменение и возвращаемое значение
receiver; определить порядок вычислений и отказ для недопустимого получателя.
Метод не вводит неявную ссылку, заимствование, выделение памяти или эффект.
Операции над общим состоянием требуют state. Mutable receiver со ссылочной
семантикой допустим только после отдельного явного контракта, а не как сахар
над нынешними значениями. Конфликт поля/метода и выбор через import должны иметь
однозначный результат либо диагностику, без поиска подходящей перегрузки.

**Интерфейсы.** Определить номинальную идентичность, владельца объявления и
разрешённое место реализации; для пары тип/интерфейс не должно быть конкурирующих
реализаций из разных зависимостей. Зафиксировать точное соответствие параметров
и результата, а эффекты реализации должны быть подмножеством объявленных.
Generic-тело проверяется по ограничениям до зависимого использования: обращаться
к неописанному методу нельзя даже при случайно подходящем конкретном типе.
Для динамического пути заранее ограничить сигнатуры: generic-методы и возврат
неизвестного конкретного Self не разрешать без отдельного решения о представлении.
Само введение интерфейсов не меняет FFI ABI 1: такие значения нельзя передать
в C как новый ABI-тип без отдельного контракта и проверки.

**Память и ресурсы.** Описать копирование интерфейсной оболочки и захватов,
владельца скрытого значения, GC descriptors/roots и время жизни таблицы вызовов.
Явно определить, означает ли упаковка копию значения или разделение идентичности,
какие выделения возможны и когда они освобождаются. Закрытие ресурса через один
alias не должно оставлять другой рабочим; наличие замыкания/оболочки не отменяет
close. GC освобождает память, но не заменяет закрытие файлов, окон и native handles.
Нужны контракты 0.8, проверка удержанных callbacks и запрет вызова после закрытия.

**Эффекты и подмена.** Сохранить проверку по сигнатурам, в том числе через generic,
метод, интерфейс и callable; публичная функция не расширяет эффекты неявно.
Выбор более точных категорий обосновать проверяемой задачей:

| Кандидат, не действующее имя | Проверяемое различие |
|---|---|
| Сеть | Локальная операция и сетевой обмен имеют различимые зависимости |
| Часы | Текущее время можно заменить управляемыми тестовыми часами |
| Внешняя случайность | Получение энтропии отличается от вычисления генератора с явным seed/состоянием |
| Приостановка | Компилятор или иной определённый механизм проверяет допустимость ожидания в UI/callback |

Решить, какие различия выражаются отдельными эффектами, а какие — параметрами
интерфейса. Не вводить категорию, для которой нет поведения, диагностики и теста.
Сеть применяется при реализации 0.11.2; модель приостановки окончательно связывается
с event loop в 0.10.11 и реализуется в 0.11.1. Для io/args/state/process нужны
явная политика совместимости, миграция builtin-каталога и точные diagnostics.
Тестовая реализация может иметь меньше эффектов; вызов через общий интерфейс
проверяется по его объявленному контракту. Управляемый PRNG не обязан получать
эффект внешней случайности; чтение/изменение его общего состояния требует state.
Выделения под неизменяемые значения не становятся новым эффектом автоматически.

FFI остаётся доверенной границей: объявление «чистого» метода не доказывает
поведение DLL. Не ослаблять действующие обязательные эффекты extern ради удобной
сигнатуры. Capabilities ограничивают операции через API, но не заменяют ОС-песочницу.
Replay проверяет запросы и ответы выбранных интерфейсов, а не обеспечивает
детерминизм произвольной программы с произвольным native-кодом.

## Порядок и доказательство пользы

В 0.10.1 принимаются контракты, затем 0.10.2–0.10.6 дают абстракции; 0.10.7–0.10.8
применяют их к внешним зависимостям и replay. Callbacks, GUI и совместный async-
контракт идут в 0.10.9–0.10.11. Прежние шесть обязательств версии сохранены
с таблицей перенумерации в roadmap. Этапы 0.8/0.9 не переставляются.

Сквозной пример — приложение с закрытой моделью документа/настроек и интерфейсом
хранилища: файловая и тестовая реализации используют один клиентский алгоритм.
Generic-тест проверяет обе реализации; отдельный сценарий выбирает реализацию
при запуске и хранит её как интерфейсное значение. Варианты с ошибкой чтения,
записи и закрытия проверяются на независимых ожидаемых результатах.
GUI использует эту же модель и зависимости; изменённый внутренний layout модели
не требует изменения клиента при пересборке. Время/случайность тестируются отдельно
с фиксированными ответами, затем проверяется запись и replay без реальных действий.

Отрицательные проверки: обход privacy/конструктора, утечка private-типа,
неполная/двойная реализация интерфейса, неверные параметры/результат, лишний эффект,
вызов без ограничения, недопустимая динамическая сигнатура и закрытый ресурс.
Положительные/граничные: порядок вычислений receiver, aliasing и value copies,
GC на каждой подходящей точке, циклы захватов, reentrancy, повторное закрытие,
новая реализация из отдельного модуля, rename и навигация к объявлению/реализации.

Перед зависимой миграцией selfhost/tools выполняется bootstrap-переход; реализация
обновляет checker/HIR/backend раздельно. Для новых конструкций проверяются fmt,
CLI/LSP/MCP и новый агент со skill. Full native verify, C recovery и clean delivery
обязательны в gate 0.10; видимое GUI и работа пользователя проверяются отдельно.
Сравнить static/dynamic вызовы, число выделений, удержанную память, размер кода
и время компиляции по заранее зафиксированным бюджетам; нулевая стоимость не обещается.

## Что не добавляем в этот этап

Наследование реализации и его переопределения, множественное наследование,
неявная структурная типизация, reflection/downcast, специализация и associated
types, пользовательские effect handlers. Возвращаться к ним следует по конкретной
прикладной потребности после проверки минимальной модели; они не подразумеваются
словом «ООП» и не являются обещаниями выпуска 1.0.
